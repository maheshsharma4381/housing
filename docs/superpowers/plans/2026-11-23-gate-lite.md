# Gate Lite Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A shared gate phone records each visitor (flat, name, purpose, photo), calls the flat in one tap, tells the household, and gives the committee a register it can download.

**Architecture:** Gate logins live in a new `gate_accounts` table, outside `society_memberships`, so no existing "any member" policy reaches them; every gate action is a `SECURITY DEFINER` RPC that checks an active, claimed gate account. A trigger keeps a gate login from ever becoming a member. Visitor rows live in `gate_entries` with RLS for the committee and the household; photos sit in a private `gate-photos` bucket and are removed after 90 days by a server route the daily cron calls.

**Tech Stack:** Next.js 15 App Router, React 19, Tailwind v4, Supabase (Auth, Postgres, Storage, pg_cron, pg_net), PGlite DB tests, `node --test` unit tests.

**Spec:** `docs/superpowers/specs/2026-11-23-gate-lite-design.md`

**Two choices the spec left open, made here:** the Call list comes back with the save (`gate_log_entry` returns `calls`), so spec section 6's `gate_flat_contacts` is folded into it; and spec 5.7's "signed URLs created by an RPC" becomes a storage SELECT policy (`can_view_gate_photo`) plus the Storage client's `createSignedUrl`, because Postgres cannot sign storage URLs. The rules are the spec's.

## Global Constraints

- Start only after mobile login is live (`NEXT_PUBLIC_PHONE_LOGIN=1` in production). Gate accounts log in by mobile code only; no email gate accounts.
- One migration: `src/db/migrations/040_gate_lite.sql`; then `bun run db:bundle`. Never edit 001–039. Redefined functions are copied verbatim from their latest migration and changed only where this plan says.
- Every new function: `SECURITY DEFINER SET search_path = public`; helpers revoked from `PUBLIC, anon, authenticated`; RPCs granted to `authenticated` only.
- App UI text is English only. Gate screen: large targets, icons, few words.
- Gate Lite is on every plan, Free included. The gate screen never renders an ad slot.
- At most 5 gate accounts per society. Photo ≤ 1280 px on the long side, about 200 KB, JPEG. Photos removed 90 days after the entry; entries deleted after 2 years.
- Purposes, exactly: `guest`, `delivery`, `cab`, `service`, `other` (labels Guest, Delivery, Cab, Service, Other).
- Notification: kind `visitor`, title `Visitor at the gate: {name}`, body the purpose label, link `visitors`. "Society office" entries notify nobody; Exit notifies nobody.
- DB tests run one file at a time: `TZ=UTC node --test tests/db/<file>.test.mjs`. Unit tests: `node --test tests/unit/<file>.test.ts`; lib files imported by node tests use `.ts` extensions in their own imports.
- Commits on branch `gate-lite` with `git -c user.name=ved300406 -c user.email=ved300406@gmail.com commit ...`, message ending `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Never push; never run `bun run db:migrate --apply`.

## Review Focus

1. A guard double-taps Save on a slow connection: one entry and one notification, not two (pinned in Task 3: `gate_log_entry` is idempotent on `p_client_id`).
2. Flats `A-101` and `B-101` both exist: the guard can tell them apart and the entry lands on the right one (pinned in Task 3: `gate_flats` returns `wing`; Task 6 renders `flatLabels`).
3. A tenant moves out (membership switched off): the next visitor notifies and lists the owners, and the old tenant no longer sees the flat's visitors (pinned in Task 3).
4. The photo upload fails or the guard skips it: the entry still exists, Call still works, and the register shows "No photo" (pinned in Task 4: `gate_set_photo` is separate and optional).
5. The society is deactivated or the gate account switched off mid-shift: every gate RPC refuses at once with the spec's switched-off message (pinned in Task 1 and Task 3).
